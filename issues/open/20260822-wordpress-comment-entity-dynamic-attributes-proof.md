## Goal

Stock WordPress 7.1 の Comment entity と CommentMeta を、Hibari core に WordPress-specific comment abstraction や aggregate engine を追加せず、既存 SchemaIR / QueryIR / MutationIR と Dynamic Attributes で成立させる。

Posts/PostMeta、Users/UserMeta に続く3つ目の `ordinary entity + Dynamic Attributes` consumer proof とする。

## Source-derived constraints

Stock `wp_insert_comment()` は:

- `wp_comments` に row をinsertする
- generated `comment_ID` を得る
- approved commentでは post comment-count maintenanceを起動する
- `get_comment()` で保存結果を再取得する
- `comment_meta` が渡された場合は `add_comment_meta()` で保存する

Stock `wp_update_comment()` は:

- `get_comment(..., ARRAY_A)` で既存rowを読む
- merged comment rowをupdateする
- optional `comment_meta` を `update_comment_meta()` で更新する
- comment-count maintenanceを起動する

Comment count maintenanceは `SELECT COUNT(*)` を含むaggregate side domainであり、このchildでは有効化しない。

## Model projection

```text
wp_comments
  comment_ID           -> Comment.id
  comment_post_ID      -> Comment.postId
  comment_author       -> Comment.author
  comment_author_email -> Comment.authorEmail
  comment_author_url   -> Comment.authorUrl
  comment_author_IP    -> Comment.authorIp
  comment_date         -> Comment.date
  comment_date_gmt     -> Comment.dateGmt
  comment_content      -> Comment.content
  comment_karma        -> Comment.karma
  comment_approved     -> Comment.approved
  comment_agent        -> Comment.agent
  comment_type         -> Comment.type
  comment_parent       -> Comment.parentId
  user_id              -> Comment.userId

wp_commentmeta
  meta_id    -> DynamicAttribute.id
  comment_id -> DynamicAttribute.ownerId
  meta_key   -> DynamicAttribute.key
  meta_value -> DynamicAttribute.value
```

Backend App IDs / field codes remain only in backend fixture/configuration.

## First proof scope

Use unchanged stock public APIs:

```text
wp_defer_comment_counting(true)
wp_insert_comment(..., comment_meta => ...)
get_comment(...)
get_comment_meta(...)
wp_update_comment(..., comment_meta => ...)
get_comment(...)
get_comment_meta(...)
```

Create one unapproved comment (`comment_approved = 0`) against a deterministic post ID fixture. The Post entity itself is not mutated by this proof.

Verify:

- generated integer Comment identity
- persisted post ID / author / email / content / approval state
- later `get_comment()` reads backend state
- initial CommentMeta row is persisted through Dynamic Attributes
- `wp_update_comment()` changes ordinary Comment content
- optional comment metadata update is visible through later Metadata API read
- Comment identity remains stable

## Comment-count boundary

Set `wp_defer_comment_counting(true)` for the focused proof and do not flush it within this child.

This is intentional scope isolation, not silent emulation:

- Comment entity semantics are proven
- CommentMeta semantics are proven
- `COUNT(*)` comment-count maintenance remains unsupported/unproven
- no fake aggregate result is returned

A later child may model count maintenance explicitly if useful.

## SQL boundary

Support only exact stock shapes needed by this proof:

- `SELECT * FROM wp_comments WHERE comment_ID = ... LIMIT 1`
- exact `wp_comments` INSERT generated by `wpdb->insert()`
- exact `wp_comments` UPDATE by `comment_ID`

Translate them to ordinary `Comment` QueryIR / MutationIR. Do not broaden arbitrary `WP_Comment_Query`.

## CommentMeta / Dynamic Attributes

Reuse the configurable WordPress `MetadataSqlTranslator` introduced for PostMeta/UserMeta.

CommentMeta supplies only:

- table suffix `commentmeta`
- owner column `comment_id`
- id column `meta_id`
- model `CommentMeta`
- stable WordPress diagnostic code

No new core metadata abstraction is permitted.

## Acceptance criteria

- [ ] no WordPress Comment concept is added to Hibari core
- [ ] Comment is an ordinary backend-neutral model using existing QueryIR / MutationIR
- [ ] CommentMeta reuses the configurable Dynamic Attributes translator
- [ ] stock `wp_insert_comment()` creates one Comment through KintoneBackend
- [ ] stock `get_comment()` observes created backend state
- [ ] initial `comment_meta` is persisted and readable through Dynamic Attributes
- [ ] stock `wp_update_comment()` persists a basic content update
- [ ] updated metadata is visible through stock Metadata API
- [ ] comment identity remains stable across update
- [ ] comment-count aggregate maintenance is explicitly deferred, not emulated
- [ ] arbitrary `WP_Comment_Query`, JOIN, aggregate, transaction, and DDL remain unsupported unless already proven elsewhere
- [ ] WordPress/core contain no kintone App ID / field code
- [ ] previous core/kintone/Prisma/WordPress proofs remain green

## Guardrails

- do not add aggregate execution just for comment counts
- do not add a Comment-specific core contract
- do not duplicate MetadataSqlTranslator for commentmeta
- do not implement arbitrary `WP_Comment_Query`
- do not add moderation/status workflows beyond the persisted approval scalar in this child
- do not add notifications/email behavior
- do not add comment deletion/cascade
- do not add nested comment traversal
- do not require live kintone credentials

## Completion evidence required

- stock WordPress 7.1 public Comment/Metadata API output
- fake Kintone request evidence for Comment create/read/update
- Dynamic Attributes evidence for CommentMeta create/read/update
- proof that no comment-count aggregate query is sent to Hibari
- full CI with all previous proofs green
- exact revision/run recorded before moving to `issues/closed`

## Non-goals

- comment count recomputation
- arbitrary `WP_Comment_Query`
- moderation/status-transition workflows
- notifications/email
- threaded descendants traversal
- comment deletion/cascade
- live kintone credentials
